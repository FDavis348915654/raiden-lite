# TECH.md · 技术实现说明

> 这份文档回答一个问题：**这个游戏是怎么跑起来的**。
> 玩法、数值、关卡设计看 [README.md](README.md)；踩过的坑和硬性约定看 [../CODEBUDDY.md](../CODEBUDDY.md)。
> 本文只写"架构与实现"，数值一律引用 `js/config.js`，不在文档里重复抄。

---

## 1. 技术选型

**没有游戏引擎，没有框架，没有构建工具，没有运行时依赖。**

| 项 | 结论 |
|---|---|
| 引擎 | 无。渲染、循环、碰撞、粒子、存读档全部手写 |
| 框架 | 无。没有 React/Vue/Pixi/Phaser |
| 构建 | 无。没有 `package.json`、`node_modules`、bundler，也没有 `tsc` |
| 模块 | 无 ESM/CJS。7 个全局脚本靠 `<script>` 顺序加载 |
| 素材 | 无外部素材。美术由 Python 脚本生成，音效由 WebAudio 实时合成 |
| 第三方库 | 0（运行时）。工具链只用 Pillow / numpy / Playwright |

选这条路的**唯一理由**是目标平台：这个 Demo 最终要移植到小米手环 10（Vela 快应用），包体、内存、启动时间都卡得很紧，塞一个 JS 游戏引擎不现实。而 480×854 的竖版 STG 需要的渲染能力只有"贴图 + 半透明 + 叠加混合 + 少量径向渐变"，Canvas 2D 完全够用。

副作用是**所有轮子都得自己造**：图集打包、粒子系统、缓动、UI 热区、音效合成、崩溃兜底。这部分工作量的绝对值不小，但换来的是"打开 `index.html` 就能玩、改一行 JS 刷新即生效"的迭代速度。

如果哪天要做 3D、骨骼动画或联机，再评估迁到 Cocos / PixiJS 更划算——现在的代码是"按引擎的职责分层、但不依赖引擎"的写法，迁移成本主要在渲染层。

## 2. 运行时栈

| 层 | 用什么 | 关键实现 |
|---|---|---|
| 渲染 | **Canvas 2D** | `canvas.getContext('2d', { alpha: false })`，单画布，无 WebGL |
| 循环 | `requestAnimationFrame` | 固定步长累加器 `STEP = 1/60`，`dt` 夹到 0.1，单帧最多追 5 步 |
| 音频 | **WebAudio** | `OscillatorNode` + `GainNode` 包络做音效；噪声走 `AudioBufferSource` + `BiquadFilter` 带通 |
| 输入 | **Pointer Events** | `pointerdown/move/up` + `pointerId` 记录控制权归属；键盘为辅助 |
| 存档 | `localStorage` | 只有最高分，键 `raiden-lite.hi.v1` |
| 画布尺寸 | 逻辑分辨率 + CSS 缩放 | 逻辑坐标恒为 480×854，DPR 上限 2 |

## 3. 启动与加载

`index.html` 只有 27 行，本质上是一份"加载清单"：

```html
<script src="js/config.js?v=3.38.0"></script>   <!-- 1. 纯数据：所有数值表 -->
<script src="js/audio.js?v=3.38.0"></script>    <!-- 2. SFX 原语 -->
<script src="js/atlas.js?v=3.38.0"></script>    <!-- 3. 图集帧表（生成物） -->
<script src="js/assets.js?v=3.38.0"></script>   <!-- 4. 图片加载 + 绘制封装 -->
<script src="js/entities.js?v=3.38.0"></script> <!-- 5. 各对象自身行为 -->
<script src="js/levels.js?v=3.46.0"></script>   <!-- 6. 编队几何 + BOSS 弹幕 -->
<script src="js/game.js?v=3.38.0"></script>     <!-- 7. 主循环 + 状态机 + 碰撞 -->
```

**加载顺序就是隐式依赖链**，倒过来会立刻 `undefined`（比如 `assets.js` 里的 `ATLAS` 来自 `atlas.js`，`entities.js` 里的 `ENEMY_DEFS` 来自 `config.js`）。新增文件必须插在正确位置并带 `?v=`。

启动流程：`Assets.load()` 用 `Promise.all` 并行拉 `sprites.png` 与 9 张背景图 → 全部 `onload` 后标记 `ready` 并预烘焙子弹贴图 → 才能进标题页。加载期的 `LOADING…` 是 `index.html` 里的静态 `div`，不参与 Canvas。

**版本串（`?v=`）是硬性要求**：`index.html` 8 处 + `assets.js` 里拼一次。漏一处的症状不是报错，而是"版本号是新的、画出来还是旧的"——因为浏览器把 `sprites.png` 缓存住了，而 `atlas.js` 的帧坐标已经更新，表现为全屏精灵错位。

## 4. 主循环

`Game.start()` 里一个 `loop(ts)` 函数，结构是"固定步长更新 + 每帧绘制 + 异常隔离"：

```js
const raw = (ts - this.last) / 1000;
const dt = Math.min(0.1, raw);      // 单帧最大 0.1s，切回前台不追命
this.acc += dt;
while (this.acc >= STEP && guard++ < 5) {   // STEP = 1/60
  this.update(STEP);                        // 逻辑永远按 1/60 推进
  this.acc -= STEP;
}
this.draw();                                // 绘制跟着 rAF 的实际频率
```

四个设计点：

1. **逻辑与绘制解耦**。逻辑固定 1/60，物理/碰撞/计时不会因为掉帧而变速；绘制随 rAF，掉帧只影响画面流畅度。
2. **追帧上限 5 步**。一次卡顿后最多补 5 帧，剩下的直接丢弃（`acc` 继续累积到下一帧），避免"越卡越追、越追越卡"的死亡螺旋。
3. **`dt` 夹到 0.1**。切后台再回来，`raw` 可能是几十秒，不夹的话一帧要跑上千步。
4. **`update` / `draw` 各自 try-catch**。异常进 `_onCrash()` 记 `crashCount` 并继续跑，不白屏；冒烟脚本就是靠这个字段判失败。

另有 **1 秒看门狗**（`setInterval`）：切后台或异常导致 rAF 静默停掉时自动重启循环，`document.hidden` 期间跳过。

## 5. 渲染

### 5.1 分辨率与适配

- 逻辑坐标恒为 **480×854**（9:16），代码里所有坐标都按这个算，不写设备像素。
- `resize()` 做两件事：① 算 `scale = min((innerW-8)/480, (innerH-8)/854)` 设 CSS 尺寸；② 把 canvas 的 backing store 按 `min(2, devicePixelRatio)` 放大，再 `ctx.setTransform(s, 0, 0, s, 0, 0)`，这样绘制代码仍然用逻辑坐标，但输出是视网膜清晰度。
- DPR 封顶 2：3 倍屏上再往上加只多耗填充率，肉眼几乎无差。

### 5.2 绘制顺序

没有场景图、没有 zIndex。**顺序由 `Game.draw()` 里的显式调用顺序决定**，要调层就得改那几行的先后：

```
震屏 translate（包在 save/restore 内，只作用于世界层）
├─ _drawBg            滚动背景 + 70 颗视差星
├─ BOSS 战 / 通关压暗
├─ 拾取物 → 敌机 → 蛇 → BOSS
├─ 子弹 → 保险投掷物/特效 → 粒子 → 阵亡残骸
└─ 玩家 → 玩家激光 → 碰撞盒
restore（震屏结束）
├─ _drawArcs          电弧（画在震屏之外，避免长线条抖动时端点错位）
├─ 预警标记 + HUD
├─ 结算/标题 overlay
└─ 版本号 · 声音按钮 · 调试面板 · 受击红晕 · 保险白闪
```

**为什么"震屏只包世界层"**：HUD、版本号、按钮跟着晃会让人找不到按钮；而受击红晕、白闪这类全屏效果必须铺在最上面。

### 5.3 绘制预算

- 同屏活跃子弹通常几十颗（冒烟抽样 5~30），每颗一次 `drawImage`（预烘焙的小图），不做实时渐变。设计上限按 150 控——再往上单帧绘制会开始吃掉填充率。
- 粒子池 520，同屏活跃通常一两百以内，每个是一次 `arc` 填充或 `drawImage`。
- 背景是**单张 480×854 的 png 纵向平铺两次**（`drawImage` 两次 + 一个坐标取模），不是瓦片地图。
- 混合模式只在局部用 `globalCompositeOperation = 'lighter'`（发光、电弧、护盾），大面积叠加在低端设备上填充率吃不消。

## 6. 对象池

`Bullet` / `Particle` / `Pickup` / `Enemy` 全部是**定长数组 + 布尔 `active`** 的复用对象，没有真正的运行时分配：

| 池 | 容量 | 备注 |
|---|---|---|
| `bullets` | 680 | 玩家 + 敌方共用，靠 `b.friendly` 区分 |
| `enemies` | 120 | 3.28 从 90 上调：后期同屏峰值 70~80，池子见底会**静默少放怪** |
| `particles` | 520 | |
| `pickups` | 48 | 3.29 从 32 上调：四周补给放开后"掉了但没生成" |

取用是线性扫描 `arr.find(o => !o.active)`。定长数组 + 线性扫在这个量级（百级）比对象池索引管理更简单，也比每次 `new` 更便宜。

**代价是 `init()` 必须逐项复位**。池对象最典型的故障不是崩溃，而是"上一只的状态漏到下一只身上"：3.30 的"BOSS 分身隐形但打得掉"就是 `Enemy.init()` 漏清 `snakeLink`，而 `Enemy.draw()` 见到它就整只跳过。约定：**任何"外部置位、`draw`/`update` 里读"的字段，必须在 `init` 里给默认值**。

容量见底时的行为是**静默失败**（`spawn` 直接 return），不报错。所以调高同屏上限时必须同步加池子。

**例外：队友不走池（3.73）。** 同屏上限 3 架、每关清空、每架只在关内活一次，
池化省下的那点分配成本，抵不上"池对象残留状态"的风险——`Ally` 有 `kind / side / lv / weapons / slotT / shotQ` 一整套状态要逐项复位。
直接用 `new Ally()`，由 `game.allies` 数组持有，死亡后从数组里 `splice`。

## 7. 资源系统

### 7.1 图集

所有精灵打在一张 `assets/sprites.png`（1907×474，25 帧）里，帧表是 `js/atlas.js` 的 `ATLAS`：`{ 名字: [x, y, w, h] }`。绘制走 `Assets.draw()`，内部是九参 `drawImage(sheet, sx, sy, sw, sh, dx, dy, dw, dh)`。

`atlas.js` 与 `sprites.json` 都是 `tools/gen_assets.py` 的输出，**不要手改**：手动改坐标会和 png 错位，而错位的表现是"整屏精灵都画错地方"，看起来像图坏了。

### 7.2 染色贴图（受击闪红）

`Assets.drawTinted(ctx, name, cx, cy, scale, color, alpha, rot)`（3.83）：把某一帧预烘成"整体偏某色"的图，
首次用到时建一张离屏 canvas——先 `drawImage` 原帧，再 `globalCompositeOperation = 'source-atop'` 填色
（只染已有像素，不会把柔光边缘糊成方块），按 `帧名|颜色` 缓存，图集重新加载时清空。

为什么不实时叠一层：在深色背景上"原图 + `lighter` 叠白"读起来是**变亮**，
而变亮在这套游戏里一直是拾取/增益的语言（3.83 之前玩家反馈受击像吃了道具）。
红色必须真的换掉机身颜色，所以要么预烘、要么每帧建 canvas——后者是 7.2 那条已经踩过的坑。

受击链路：`Player.hit()` / `Ally.hit()` 置 `hurtT / hitT`（0.18s）→ `draw()` 在正常贴图之后
叠一张 `HURT_COL`（`#ff4d4d`）染色版，alpha 随时间线性衰减。队友的"被弹开"那一路
仍然是冷青小火花且**不**染色——红 = 真扣血、冷青 = 没打进去，这个二分是玩家判断
"能不能往它身后躲"的依据。

### 7.3 子弹贴图预烘焙

`Assets._buildBullets()` 在加载期用**离屏 canvas** 给每种子弹画一遍 `radialGradient`（核心亮斑 + 光晕 + 透明边），存成小图。运行时 `drawBullet()` 只做 `drawImage`。

为什么不实时画：一帧建 150 个渐变对象，在低端设备上直接掉到 30fps。这是本项目里唯一一处"空间换时间"的批量优化。

宽头弹（`wide`）走的是同一函数里的 `makeBar(54, 20)`：它是一道横向能量刃，通用 `make()` 的椭圆核铺在横向画布上仍像个扁球，所以单独用"横向线性渐变 + 两端收尖"烘焙。

**动感不靠贴图，靠 `Bullet._tempFx()`**（3.42）：追踪弹的三层尾焰、宽头弹的同形状残影与吞弹白闪都在这里画，调用点在 `Bullet.draw` 贴图之前。它只使用路径和**重复绘制已烘焙贴图**，全流程不新建渐变——每帧为十几颗子弹建渐变是这类特效最容易悄悄吃掉帧数的写法。

**尾焰有自己的一套朝向**（3.44）：`Bullet.rot` 是弹体，`Bullet.trailA` 是火焰。后者每帧朝实际速度方向做一阶低通（时间常数约 0.17s），转弯时两者夹角可达 0.6~0.9 rad。绘制时把这段夹角换算到弹体本地坐标——末端落在 `(-len·sinδ, len·cosδ)`，中间用二次贝塞尔连接——于是火焰从喷口出去、逐渐被甩向弯道内侧，成一条弧；三层再各乘 1.35/1.0/0.6 的滞后系数，外侧低速余焰甩得最开、内芯紧跟喷口，转弯瞬间看起来是"撕开成扇形"。若直接 `ctx.rotate(rot)` 后画一段直线锥形，火焰就会跟着弹体贴图整体刚性旋转，那是转弯"生硬"的唯一来源。

### 7.4 背景

9 张 512×512 的 png，每关一张，`_drawBg()` 里按 512px 高度纵向无缝平铺（`bgScroll % 512`，铺满 854 高需要 2~3 片），再叠 70 颗 `lighter` 混合的视差星点 + 一层中心提亮的径向渐变（用来压住平铺接缝）。滚速由关卡配置控制。

## 8. 音频

`js/audio.js` 是一个两百多行的 `SFX` 单例，**不含任何音频文件**，全部实时合成：

| 原语 | 实现 | 用途 |
|---|---|---|
| `_tone(freq, dur, type, gain, slideTo)` | `Oscillator` + `Gain` 包络（8ms 上冲、指数衰减） | 射击、拾取、UI、报警 |
| `_noise(dur, gain, freq, q)` | 白噪声 `AudioBuffer` + `BiquadFilter` 带通 | 爆炸、撞击、破盾 |

工程约束：

- **`master.gain = SFX_VOL = 1.00`**（3.80 定稿）。合成音是"裸正弦/方波"，早期怕刺耳只给了 0.22，结果手机外放时射击声被环境噪完全盖掉；两次上调（0.30 → 0.55 → 1.00）后实测最响的组合仍在一半刻度以下：`bomb()` 峰值 0.46、5 颗大爆炸连炸 0.39、连续开火 0.16，没有削波。**没有加限幅器**：master 后串 `DynamicsCompressor` 试过，0.06 秒的开火声整段落在 attack 里被压掉四成，密集开火反而更小。以后加音效先离线量峰值，单条超过 0.8 就调它自己的 gain。**只写一处**——`init()` 与 `setEnabled()` 各写一个数值曾出现过"初始化按旧值、切开关按新值"的不一致。
- **必须用户手势后才能播**。`init()` 在首次 `pointerdown` / `keydown` 里调用；`ctx.state === 'suspended'` 时 `resume()`。这在移动端是硬限制，不是 bug。
- **限流 `_gate(key, ms)`**：每个音效各自配阈值（射击 40ms、狙击蓄力 110ms 等），同一音效在阈值内不重复触发，否则密集弹幕会糊成一段噪声。
- **总开关走 master 增益**，用 `setTargetAtTime` 做 20ms 淡入淡出，避免"咔"的爆音；已经在排程的音也会一起收掉。

## 9. 输入

统一用 **Pointer Events**，一套代码同时覆盖鼠标、触屏、手写笔。

| 输入 | 处理 |
|---|---|
| 拖动飞机 | `pointerdown` 记录 `pointerId` 并进入拖拽；`pointermove` 只在 `e.pointerId === input.pointerId` 时响应 |
| 键盘 | `←→↑↓` / `WASD` 移动；`Q` 循环切槽、数字键 `1~4` 精确切槽；`X` 清屏炸弹、`Z` 激光保险（左右两颗大招各占一个相邻键）；`Esc`/`P` 暂停；`Space`/`Enter` 开始与续关（**开火是自动的，没有开火键**） |
| HUD 按钮 | 保险、激光保险、声音、暂停、武器槽、`DEV` 面板——热区坐标与绘制**共用一份常量**（`BOMB_BTN` / `PAUSE_BTN` / `SLOT_UI` 等），改位置只改一处 |
| 暂停按钮（3.41） | HUD 右上角血条下方的小圆，只负责"进暂停"；恢复仍是点击屏幕任意处。判定要排在"暂停中任意点击恢复"之前，否则暂停里点它等于没点 |
| 后台暂停 | `document.hidden` 时自动 `paused = true` |

**`pointerId` 是必须的**：输入只有一个 `pointerActive`，`pointerup` 又不看是谁抬的手。一只手拖飞机、另一只手点保险，抬保险那根手指就会把拖动状态清掉，玩家感受是"飞机卡住，要重新触屏"。所以 `input.pointerId` 记控制权归属，`pointermove` / `pointerup` 都要先比对它；新增触屏控件的按钮分支必须**在赋值之前 return**，不能抢走控制权。

## 10. 存档

只有最高分，键 `HI_KEY = 'raiden-lite.hi.v1'`。

- 每帧在状态机之外更新内存值（`_updateHiScore`），否则"通关 +2000 分"那句结算不算进去。
- 写盘做 1.2 秒节流，失败/通关时立刻落盘。
- **读不到存储（隐私模式 / 禁用存储）必须当 0**：一个记录分数不能把游戏搞崩。

## 11. 代码分层

没有引擎的"节点树/组件系统"，但职责划分是按引擎的思路来的：

| 文件 | 角色 | 类比 |
|---|---|---|
| `config.js` | 纯数据。所有数值、表、常量 | 配置表 + 预制体参数 |
| `entities.js` | 单个对象**自身**的行为：移动、绘制、受击 | 组件 |
| `levels.js` | 编队几何、BOSS 弹幕模式、判定轮廓 | 关卡资产 + 行为树 |
| `game.js` | 状态机、碰撞结算、投放、HUD、主循环 | 系统调度器 / 场景 |
| `assets.js` + `audio.js` | 资源与音效 | 引擎的 Resource / Audio 模块 |

**状态机**：`title → intro → warn → play → boss → clear → (下一关 | win) / gameover`。

一条重要纪律：**状态分支要共用更新入口**。按 `state` 分叉时，别在每个分支各抄一份"要更新什么"——保险/激光/冲击环/冷却统一走 `_updateBombSystems(dt)`，四个战斗状态都调。3.20.4 就是预警分支漏抄，导致炸弹挂在半空、特效定格。

**出手闸门只有一处**（3.51，3.52 分两档）：`Enemy.shoot()` 开头 `if (!this.inPlay(game)) return;`。严格档判"贴图四边都在可活动区里"，顶部要让开 `PLAY_TOP`（HUD）；压制档只对 `LEVELS[].edgeFire` 点名的机型放行到"贴图与可活动区重叠四成"，用来在屏幕边缘铺弹幕墙。两档都写在唯一的开火出口上，而不是每个 AI 分支各写一份 `y > PLAY_TOP`：那种写法只要求**圆心**过线，机身还压在血条后面就能出手，实测第 5 关火焰机 124 发里 47 发就是这么打出来的，玩家读到的是"屏幕外射来的弹幕"。压制档必须按关卡点名——全场默认会让每关顶部都挂着一层来源不清的弹。配套：`_updateEntry` 的"已入场"判据也是露出四成，否则侧向入场的单位会在打不动的那半秒里贴着边开火；主动作（浮雷爆散、BOSS 浮游炮）各自的生成点仍要夹进画面，闸门管不了"弹从哪冒出来"。

**路径型 AI 按弧长参数化**（3.54，`Enemy._patrolStep`）：`patrol` 的"双 U"环线由 5 段（直线 / 半圆 / 直线 / 半圆 / 直线）解析拼成，状态只有一个 `pathS`（已走过的弧长）。不按角度积分是因为掉帧时每帧转角的误差会累积成几何误差——同样 60 帧走完，30fps 那次的第二个弯半径会明显偏小。按弧长走，"走过多少 px 就在第几段"，帧率只影响快慢、不影响轨迹。机头方向用 `rot = atan2(-dx, dy)`：贴图默认机头朝下（`rot = 0`），这个式子让旋转后的朝向正好等于路径切线；不要照抄 `atan2(dy,dx) + π/2`——那个式子在这个贴图上让机头逆着飞行方向。

**自机判定要画出来，而且与判定同源**（3.56）：玩家真正吃弹的范围只有 `PLAYER.hitR`（6px）那个圆，贴图视觉却是 40×47——不打开 `_drawHitboxes` 的话，玩家只能凭"机身边缘好像算"去躲弹，挨打时觉得"明明擦过去了"。`Player.draw()` 里机身中心那圈亮核（淡填充 + 0.9px 边界环 + 脉动白芯）就是按 `PLAYER.hitR` 画的。三条要一起守住：①**尺寸只能取 `PLAYER.hitR`**，手写 8 / 10 之类的值，判定一改视觉就跟不上，又变成两套尺寸；②亮度必须压住——机身本身是浅青，`lighter` 下稍重一点就整块洗白，读起来不是"核心亮"而是"贴图掉了一块"；③**尾焰只有一条**：贴图只有一个居中喷口（`nozzle(0.50)`），双焰没有机体结构对应，也和标题页那架对不上。

**敌机激光是独立的一套，不抽 BOSS 的实现**（3.68）：`Enemy._laserStep` 只有"方向 + 计时"两件事（`0 空闲 → 1 蓄力 → 1.5 锁定 → 2 发射`），`Boss._updateLaser` 则和护盾轮转、阶段切换、可破坏部件、退场状态缠在一起，硬抽会让两边都变脏。三处必须同源：

1. **坐标**：`Enemy.laserSegs()` 是唯一的线段来源，玩家判定（`game._collide`）、绘制（`Enemy._drawEnemyLaser`）、调试线框（`_drawHitboxes`）都读它。`side` 模式返回的是一条 `0 → VIEW.w` 的贯穿线——"把画面切一刀"才是它存在的意义，只朝一侧伸等于没放。
2. **位置冻结**：蓄力/发射期间把机身速度压到 10%，做法是 `update()` 里记下 AI 之前的坐标，跑完 AI 再按 `hold` 倍回写。不逐个改 AI 分支的移动量，是因为那些分支各自推位置（正弦摆动、爬升、悬停……），九处都要记得这件事，迟早漏一处。回写排在状态推进之后——本帧刚进蓄力也要立刻减速。
3. **出手资格**：`_laserStep` 额外要求 `!entryImmune && spawnGuard <= 0`——增益门只管"该不该出手"，入场保护管"打不打得动"，一边开火一边打不动是容易读成作弊的组合。**3.71 起这里不再走 `inPlay()`**：整只进可活动区要 4.5 秒（狙击机），比它的寿命还长，光柱永远打不出来。新门槛是"贴图露出四成（即 `!entryImmune`）+ `y ≥ 96`（HUD 下沿）"——光柱是方向预告，机身压在 HUD 后面也读得懂；弹幕则必须看得见枪口，所以 `shoot()` 的 `inPlay()` 一个字没动。两者不要互相顶替。

**`holdFirst`：护盾的时间闸，不是加血**（3.71）。`ENEMY_SHIELD[kind].holdFirst` 只给带激光的机型。`Enemy.hit` 里护盾被打空时，若 `laserState === 0`（还没开始蓄力）就把 `shieldHp` 停在 1 并 return，不破盾。这条**保证"露头必放一道光柱"**，但边界卡在"开始蓄力"那一帧——蓄力/发射期间照样能被打断，否则就是"无敌到放完招"的墙。三个配套：①`init` 里同时把 `shieldDur` 拉到 `laserCd + charge + lock + fire + 0.4`，否则计时先到、盾自然消散，保底跟着没了；②绘制要单独给一个**琥珀色脉动的"锁壳"**（`draw()` 里 `locked` 分支），不然玩家看到的是"盾空了却打不进去"，像 bug；③**锁壳必须优先于受击白闪**——玩家是持续开火的，`shieldHit` 每帧被重置，白闪会一直盖住琥珀色（3.71 第一次实装就是这样，截图里整个壳全白，和普通护盾没区别）。

`Enemy.init` 里 `laserCfg / laserState / laserT / laserAng / laserCd` **必须逐项复位**：`laserState` 留成 2 会让复用的敌机一出生就顶着上一只的光柱（判定还真的算数），`laserCd` 留成负数会立刻开火。这是池对象的老坑（同 3.30 的 `snakeLink`）。

**激光按关卡点名**（3.69 用 `from`，3.81 改成 `stages`）：`ENEMY_DEFS[].laser.stages` 是关卡白名单，`init` 里判 `stages.indexOf(opt.stage) >= 0`，不在表里就 `laserCfg = null`。`opt.stage` 只由主生成路径 `_spawnEnemy` 传；判据写成"关卡信息缺失就放行"（`!opt.stage || ...`），这样 BOSS 召唤的援军、测试脚本直接 `init()` 都维持原行为。反过来把缺省当第 1 关，会让所有没传 `stage` 的调用静默失去激光——这类"少传一个可选参数就少一个机制"的写法在这里已经踩过（`spawnPlayerBullet` 的白名单）。

**别退回 `from`**：`from` 是"从第几关起解锁"，一旦解锁就不会收回。3.69 的设计里轰炸机第 2 关教完光柱，第 3~9 关只要它出场就带竖线；加上坦克机、水母、狙击机依次解锁，到第 9 关四种形态混着来，光柱从"高级武器"变成每关的背景板（实测 67 架次）。`stages` 是白名单，同一只机型照样能在别的关登场，只是不放光柱。改数量时别只看配置里的 `n`：`spawnFormation` 会按关卡 `density`（第 9 关 2.38）放大，实际架数常常是配置的两倍多。

**两道限流闸门**：`game.enemyLaserLoad(mode)` 同时返回全场条数与同形态条数，`_laserStep` 里 `total >= ENEMY_LASER.max || same >= cfg.max` 就退回 0.5 秒再来问（不要每帧扫全场）。同形态上限写在 `ENEMY_LASER.modes[].max`，因为三种形态的压迫不是一回事——只留总数时，第 6 关十几架狙击机会把 3 个名额全占住。

**教学波用 `intro` 锁住数量**（3.70 从 `noEcho` 升级）：`startLevel` 里自动补波的数量是 `Math.max(2, round(n * 0.6))`，`spawnFormation` 里还会按 `level.density` 放大 `n`——两处都会让配置里的 `n` 变成玩家实际看到的别的数字（第 2 关 1.40 密度，写 2 架出 3 架；再补一波就是 5 架）。`LEVELS[].waves[].intro` 同时关掉这两处，语义是"这一波是给玩家看清机制的，写几架就是几架"。只关一处会得到最难受的中间态：补波挡住了、密度还在放大，回看配置觉得一切正确，画面却差一架。

它和 `uo`（巡航机）、`isMiniKind`、`snake` 是补波 `if` 里的并列条件，加新的排除项往那一行加，别再抄一份。**另外它必须进 `startLevel` 重建 wave 的逐字段白名单**——那个 `arr.push({...})` 只搬它认识的字段，漏了 `intro` 就在 `spawnFormation` 里读不到（补波那边读的是原始 `w`，看起来"一半生效"，最难查）。同一个坑 3.54 的 `uo` 踩过。

**`spread` 是 `line` 编队的横向间距**，默认 66（7 架横排不出屏的上限）。2~3 架的教学波要显式拉开，否则两条光柱挤成一条粗线。同样要进重建白名单。

**队友直接复用 `Player.fireFrom`，不复制弹道**（3.73）：`Ally._fire()` 里就是
`Player.prototype.fireFrom.call(this, game, x, y, ALLY.dmgMul, lv, wi, true)`。
好处是"队友的散射炮"和"玩家的散射炮"天然一致——自己再写一份简化弹道，两者会长得不一样，玩家一眼能看出来。
代价只有两个要补的字段（`shotQ` / `boostT`），加上 `_queueShot` / `_flushShots` 两个方法：
后者用 `Ally.prototype._queueShot = Player.prototype._queueShot` 直接指过去，
以后改错峰节奏（火神炮的 0.042s）队友自动跟上。

**`game._shotMul` 必须在调用前后存 / 取。** `fireFrom` 会把它设成队友的倍率（0.6）且**不还原**，
而玩家有三把临时武器是**直接调 `spawnPlayerBullet`**、不经过 `fireFrom` 的——
它们会静默吃到这个折扣。这类"全局临时变量不还原"的坑不报错，只让某个机制悄悄变弱。

**队友挡弹排在玩家判定之前**（`_collide` 里）：同一颗弹不能既打队友又打玩家。

**队友撞机（3.76）在玩家撞机之后单独一段**，不能并进同一个 `for (enemies)` 循环：
玩家那边一旦 `if (!p.alive) return;` 就会中断整个 `_collide`，
混在一起会变成"玩家这一帧死了，队友的撞机判定就没了"。
`_canRam(e)` 是两边唯一的撞机资格判定（入场保护、底部爬升豁免、冲角型俯冲放行），
抽出来是为了不让两处判据漂移——各写一份的话，改规则时很容易只改一处，
表现为"玩家撞不到、队友能撞到"。

撞机限流用**独立的 `ramT`（0.9s）**，不是受击无敌 `invT`（0.55s）。
试过复用后者：频率太高，第 9 关 30 秒里游走型撞十几次，存活从 57% 掉到 15%。
两个计时器各管一件事，合用一个会让"它明明在无敌，却还在撞人"多出一个要解释的状态。
队友撞 BOSS 本体只扣队友血（和玩家一致），BOSS 不吃撞机伤害。

**队友受击有两个计时器，刻意不合并**（3.74）：`hitT` 0.12s 只管白闪（绘制），
`invT` 0.55s 只管判定（`hit()` 开头 return，但**子弹仍然被吃掉**——吃弹是"吸引火力"的物理形式，
把判定挪到碰撞层的 `continue` 会让这条机制静默消失）。
共用一个值必然一头将就另一头：0.12s 的白闪看不见，0.55s 的半透明读作"这架快碎了"。
无敌期要补一圈冷白冲击环，否则子弹撞上去凭空消失、读起来像判定卡了。
时长只给玩家的三分之一（1.6s → 0.55s）：队友是吸收单位，给到 1.6s 就等于打不死，
密集弹幕下每秒只吃一发，能撑半分钟。

**敌机改瞄队友放在 `Enemy.shoot()` 那处唯一的 `ang` 计算里**（3.75）：
九条 AI 分支全部汇到它，所以改一处就够，不存在"漏改某个分支导致某些敌人不打人"。
目标由 `game.pickAllyTarget(e)` 按**距离反比加权**挑（越近越容易被盯上，
但三架都有机会——直接取最近会让跟随型和驻守型永远吸不到火力）。
`nonAim` 直射型、`snipe` 狙击弹与 `ring` 环形弹不参与，BOSS 弹幕走 `BOSS_PATTERNS`，也不参与。

**数据驱动**：加一种敌机 = 在 `ENEMY_DEFS` 加一条 + 图集里加一帧；加一层波次 = 在 `LEVELS[].waves` 加一行。逻辑代码里基本不出现具体数字——这是"能用配置解决就不加抽象层"的落地方式。

## 13. 性能

目标 **60fps @ 480×854**。实测（Playwright + SwiftShader 软件渲染，抽测第 1/5/9 关）稳定 60fps —— 这是偏保守的下限，软件渲染都能满帧，真机 GPU 只会更宽裕。

已知的性能红线：

| 红线 | 原因 | 对策 |
|---|---|---|
| 每帧新建渐变 / 每帧 `new` 对象 | GC 抖动，帧时间毛刺 | 子弹贴图预烘焙；全部对象池 |
| 大面积 `globalCompositeOperation='lighter'` | 低端 GPU 填充率 | 只用于小面积光效 |
| 同屏子弹 > 150 | 每颗一次 `drawImage` + 碰撞遍历 | 池子封顶 680，弹幕设计控制在 150 以内 |
| 碰撞用 O(n×m) 双层循环 | 无网格加速 | 量级可接受（弹 ~150 × 敌 ~80），暂不引入空间划分 |

碰撞全部是**圆-圆距离平方比较**（`dist2`，不开方）+ BOSS 的多圆近似；只有 BOSS 本体用矩形。判定与绘制**必须同步**：`_drawHitboxes()` 是调试层，约定是"每一条真实判定都要画出来"，改了判定不更新它，这个开关就会骗人。

BOSS 的可破坏部件（`BOSS_PARTS`）与本体是**两条独立血条**：子弹命中先判部件圆、命中即 `continue`，所以打炮台一点本体伤害都落不到；3.49 起在 `onBossPartDestroyed()` 里补一笔本体伤害（`bossPartKillRatio`），并走 `boss.hit(..., { raw: true })` 跳过护盾轮转——它是"炮塔爆炸撕开舰体"，不是一次命中。同一条回调也被保险（`_bombBoom`）复用，所以一颗雷清掉两门会同时拿到 16% 与 `bombBossDmg`。

部件与浮游炮在 3.66 被包成**可被自动武器锁定的子目标**（`Boss._makeSubTarget`）：`x`/`y` 是 getter（跟着舰体走、浮游炮还带 36~W-36 夹边），`seq` 唯一、`hostSeq` 挡住池复用，`hit(dmg, bullet, game)` 与 `Enemy` 同构。汇总在 `boss.subs`，供 `nearestEnemy` 与 `nearestChainTarget` 扫描。以前自动武器只遍历 `enemies`，于是追踪弹永远打不到炮塔、雷电在 BOSS 战零触发。三条扣血路径（子弹、保险、雷电）统一走 `Boss.damageSub()`，`invuln` 只在那里判一次。

BOSS 轮转护盾（`boss3`）的挡弹判定在**膜上**，不在本体轮廓上（3.55，`Boss.shieldHitTest`）：膜半径走 `shieldRx = w*0.46` / `shieldRy = h*0.46`，与绘制共用同一对 getter；子弹**跨过膜的那一帧**就被拦下（用 `Bullet.px/py` 记的上一帧位置判，不是"走到膜内就挡"——后者会把从缺口穿进来的子弹在后续某帧补判成命中盾）。判定顺序放在部件与本体之前，因为膜是最外层、炮口也在膜内。

配套的三条：①`Boss.hit()` 里**不再**有按玩家坐标兜底的挡弹判定——它和命中点坐标会打架（玩家横移后，从缺口打进去的子弹被按当前方向补判成挡下），挡弹完全由拿得到真实命中点的两处负责（`_collide` 的子弹路径、`_fireLaser` 的光束路径）；②视觉必须"亮 = 有盾 = 打不进"——3.53 的挡面用的是 `stage.accent`，深海主题下比缺口那圈白虚线还暗，玩家把缺口当成了盾，机制就白做了；③挡弹反馈（火花、涟漪、该段弧闪白）要落在膜面上，把越膜那一帧的位移按归一化距离除回去，否则弹开点会比膜"陷进去"半个身位。

BOSS 出场无敌期（`boss.invuln`）**不是关掉碰撞**：`_collide` 里它走独立分支——照常调 `_bossHits()` 判命中、消耗子弹、`boss.barrierHit()` 记一圈涟漪、溅冷色火花，只跳过扣血。这样"打不动"和"打不到"在观感上是两件事，后者会被玩家当成 bug。分支写成 `if (invuln) {...} else if (boss) {...}` 而不是 `if (invuln) continue`：那条 `continue` 会连后面打小怪的循环一起跳过（第 7 关 BOSS 退场召唤期间援军就永远打不掉）。

## 14. 技术债与迁移评估

**现有取舍**（不是 bug，是明确选择的）：

- 无模块系统 → 全局命名空间，靠加载顺序。文件数涨到十几个之前够用，再涨就该上 ESM 了（不需要 bundler，浏览器原生支持）。
- 无类型 → 靠 `config.js` 的集中数值 + 命名约定。TS 化收益主要在 `entities.js`（3400 行）里，但要引入构建步骤。
- 无场景图 → 层序写死在 `draw()` 里。STG 的层序本来就固定，硬编码反而更可控。
- 无对象池索引 → 线性扫 `find(o => !o.active)`。百级容量下可接受。

**迁移到手环（Vela 快应用）需要面对的真实差异**：

| 项 | 浏览器版 | 手环版 |
|---|---|---|
| 渲染 | Canvas 2D | 快应用的 canvas 组件，能力子集，需逐项核对 `globalCompositeOperation` / `filter` |
| 音频 | WebAudio 实时合成 | 通常只能播短音频文件，"全合成"这条路走不通，需要预渲染成 pcm |
| 内存 | 无约束 | 图集要按关卡拆包，不能一次全载 |
| 输入 | Pointer + 键盘 | 触摸/表冠，热区要重排（480×854 → 方屏或圆屏） |
| 存储 | localStorage | 快应用的 storage API，需要适配层 |

细节见 `../小米手环10-雷电Lite开发方案.md` 和 README 的「与手环版的差距」一节。
